1. The big picture

crm-lead is a Customer Relationship Management system. A CRM keeps track of a company's customers and everything around them: leads (possible customers), accounts (customer companies), orders, invoices, support requests and more. You asked for 17 modules in total (users and roles, accounts, contacts, leads, opportunities, activities, marketing, products and quotes, orders, invoices and payments, support, customer portal, reports, workflow automation, documents, AI chatbot and voice, integrations).

The technology, and why each piece is there

PartTechnologyWhy (in plain words)
Website (frontend)Next.js 16, React 19, TypeScript, Tailwind CSS 4React builds the screens; Next.js runs them on a server so data and tokens stay safe; TypeScript catches mistakes before running; Tailwind gives consistent styling.
API (backend)Python 3.12, FastAPIFastAPI turns Python functions into a web API, checks incoming data automatically and documents itself (OpenAPI).
DatabasePostgreSQL 16A reliable database with strong rules (constraints, triggers, permissions) that protect data even if code has a bug.
Database codeSQLAlchemy 2, AlembicSQLAlchemy lets Python talk to the database safely (no hand-built SQL); Alembic records every change to the tables as a numbered "migration".
LoginKeycloak (OpenID Connect)A dedicated login server. The CRM never stores passwords itself; Keycloak handles passwords, sessions and two-step sign-in.
Running servicesDocker DesktopRuns PostgreSQL and Keycloak in containers, the same way on every machine, without installing them by hand.
Testspytest, Vitest, Playwrightpytest tests the backend against a real database; Vitest tests screen components; Playwright clicks through the real website like a person would.
Version controlGitKeeps the history of every change. The repository is set up but not committed yet (your choice).

The rules we agreed to follow

  • One phase at a time; stop and wait for your approval at the end of each phase.
  • Explain every step in beginner-friendly language.
  • Ask before anything destructive (deleting data or volumes, rewriting history) and before major architecture changes.
  • Never claim tests passed unless they were actually run and shown passing.
  • No cloud deployment; everything runs locally. Commands for you use Windows CMD syntax.
  • No secrets in code. Never trust IDs sent by the browser. Never let one tenant see another tenant's data.

Modular monolith

The backend is one application (a "monolith") split into clearly separated modules (backend/app/modules/<name>/): identity, accounts, contacts, leads, sales, support, orders, invoices, portal. Each module has the same files:

FileWhat it is for
models.pyThe database tables of the module.
schemas.pyWhat the API accepts and returns. Input and output are separate, so the browser can never set fields like totals or numbers.
policies.pyWho may see which rows (record-level rules), written as database conditions.
repository.pyThe database queries, always with the policy applied.
rules.pyPure business rules (status flows, money maths) that are easy to unit-test.
service.pyThe business actions (create, confirm, pay…). Never commits; writes an audit record.
router.pyThe web endpoints. Thin: check permission, call the service, commit once.
api.pyThe only thing other modules may import. Keeps modules independent.

Why: it is as simple to run as one program, but each part can be understood, tested and later split out on its own (decision recorded in docs/adr/0001-modular-monolith.md).

3. The journey, step by step

Each step below says what you asked, what was built, why, and how it was checked.

Step 1 — Planning documents (Phase 0)

You asked: plan the whole CRM (stack, 17 modules, rules) and create architecture.md, implementation-plan.md, CLAUDE.md, .gitignore and a folder structure, without building business modules yet.

What was done:

  • architecture.md: the design (modules, tenancy, security, data rules).
  • implementation-plan.md: the work split into numbered phases with acceptance criteria.
  • CLAUDE.md: the working rules, security rules and commands — read at the start of every session.

Why: agreeing on the plan first avoids rebuilding later.

Step 2 — Finishing Phase 0

You asked: git init, README, .editorconfig, .gitattributes, the first ADR, and check tool versions.

  • git init created the repository. .editorconfig keeps formatting consistent between editors; .gitattributes fixes line endings between Windows and Linux.
  • ADR = Architecture Decision Record: a short document explaining one important decision. ADR 0001 records the modular monolith.
  • You chose: "Leave it uncommitted for now; I'll set up Git, uv and Docker first." Git name/e-mail are still not set, so nothing is committed.

Step 3 — Backend foundation (Phase 2a)

You asked: a FastAPI app with a health endpoint, configuration, CORS allow-list, structured logging, consistent errors, requirements files, .env.example and pytest — without fake authentication.

  • GET /api/v1/health tells whether the API is alive.
  • Configuration comes from environment variables (prefix CRM_), never hard-coded.
  • CORS allow-list: only the CRM website (http://localhost:3000) may call the API from a browser.
  • Structured logging: every log line is JSON with a request ID, so problems can be traced.
  • Consistent errors: every error uses the "Problem Details" format with a stable code.

Checked 25 tests passing.

Step 4 — Database foundation (Phase 2b) and Docker (Phase 1)

You asked: PostgreSQL with SQLAlchemy and Alembic, no real customer data, no shortcuts instead of migrations; validate the connection. Later: a named Docker volume and a health check.

  • infrastructure/docker-compose.yml runs PostgreSQL 16 with a named volume (postgres_data) so data survives when the container is removed, a health check, and a port bound only to 127.0.0.1 (not reachable from your network).
  • Two database roles: crm_owner (changes tables, used by migrations) and crm_app (the API: may only read/write rows). If the API were ever attacked, it still could not drop tables.
  • Migration 0001: tenants, users, accounts, contacts, leads — with UUID keys, timestamps and composite foreign keys that stop cross-tenant links.
  • Docker problem: the engine would not start because Windows "Virtual Machine Platform" was off. You ran wsl --install --no-distribution and restarted; after that PostgreSQL went from "starting" to "healthy".
  • We proved persistence: the container was removed (without -v) and recreated, and the data was still there.

Checked 49 tests passing including 17 against the real database.

Step 5 — Login with Keycloak, roles and permissions (Phases 4/5, part 1)

You asked: real authentication with no hard-coded secrets, no admin credentials in files, no custom password storage, and security-focused tests.

  • Keycloak was added to Docker with a realm crm and a client crm-web. The realm file uses placeholders like ${CRM_WEB_CLIENT_SECRET}; real values are generated into the git-ignored .env.
  • PKCE login (Authorization Code + PKCE): the safest browser login flow; the password grant is disabled.
  • The API checks every token: signature (RS256), issuer, audience crm-api, expiry. Any failure gives the same generic 401.
  • Six roles: Super Admin (platform only, sees no tenant data), Tenant Admin, Sales Manager, Sales Agent, Support Agent, Customer. Each role maps to permissions like lead:read:own (file backend/app/core/auth/rbac.py).
  • ADR 0002 (you accepted it): the tenant comes from the CRM's own user record found by the token's issuer + subject — not from anything the browser sends.
  • portal_access_grants (migration 0002): which customer user may see which customer account.
  • A seed script creates fictional demo tenants, users and accounts.

Checked 152 tests passing, including tests against the real Keycloak.

Step 6 — Lead Management (Phase 7)

You asked: create/read/update leads, assign, status changes, qualify, convert (atomic, no duplicates), activities, history, search, audit — with tenant and role security and OpenAPI docs.

  • Lead status flow with only allowed changes (e.g. you cannot convert an unqualified lead).
  • Conversion creates account + contact + opportunity in one transaction: all or nothing, and a second conversion is refused even if two people click at the same time (row locking).
  • Optimistic locking: each edit sends the version it loaded; if someone else changed the lead meanwhile, you get a clear "changed by someone else" error instead of silently overwriting.
  • Audit log: every important change is recorded in an append-only table (the API cannot edit or delete it).
  • Migration 0003; API contract exported to docs/api/openapi.json.

Checked 286 tests passing.

Step 7 — Frontend workflows 1, 2 and 3

You asked: real screens connected to the real API, secure login, no tokens in localStorage, useful error messages, component and end-to-end tests, one workflow at a time.

  • Workflow 1: login/logout, dashboard, lead list (search, filters, sorting, pages), create lead.
  • Workflow 2: lead details, edit, assign, qualify/disqualify, convert — each with a confirmation dialog.
  • Workflow 3: customer account list and details, employee profile page.
  • How login is kept safe: the browser only gets an encrypted, httpOnly cookie. The tokens stay on the Next.js server ("Backend for Frontend"). An expiring token is refreshed automatically.
  • Hiding a button in the screen is only for convenience — the API checks permission again every time.

You then asked to show all modules on the dashboard: a module overview now shows every module honestly as "available" or "planned · phase N".

Checked backend 361 tests; frontend 87 component tests and 29 end-to-end tests.

Step 8 — The AI assistant request, and a decision on order (ADR 0003)

You asked for an AI assistant with strict security (verified identity, no unrestricted database access, permission checks on every tool call, prompt-injection protection, approvals for sensitive actions, evaluation tests, text before voice).

Your decisions: build the prerequisites first; use the Anthropic Claude API; use local embeddings with pgvector. Build order: customer portal → support tickets → orders → invoices → AI assistant. Reason: the assistant can only safely answer questions about tickets, orders and invoices once those exist with proper permissions.

Step 9 — Customer portal (Phase 15)

  • Customers who log in are sent to /portal; staff screens are closed to them.
  • They see only accounts listed in their portal access grants. Another customer's account — in the same or another tenant — answers "Page not found", exactly like a page that doesn't exist (so nothing leaks).
  • Portal API responses are smaller, customer-safe versions (no internal fields).

Step 10 — Support tickets with human handoff (Phase 14)

  • Tickets numbered per organisation (T-0001…), status flow New → In progress ↔ Waiting for customer → Resolved → Closed (final).
  • SLA (service-level agreement): deadlines per priority, shown as on track / at risk / breached / met.
  • Public replies vs internal notes (never shown to customers). Comments cannot be edited or deleted.
  • Human handoff for the future assistant: support.api.create_customer_ticket(..., channel="assistant") runs as the customer and only for their own accounts.
  • Migration 0004. Documentation: docs/support.md.

Step 11 — Orders (Phase 12)

You asked: orders for staff and customer portal order status, verified against the running backend.

  • Because products and quotes (Phase 11) don't exist yet, staff create orders directly with lines (description, quantity, price, tax). Line amounts are stored as a snapshot, so later price changes never alter an order.
  • Status flow: Draft → Confirmed → In fulfilment → Shipped → Delivered; Cancelled possible until shipped (reason required, shown to the customer).
  • Money is exact decimal (never floating point), rounded half-up per line; the server calculates every amount. The form shows a live preview using exact whole cents.
  • Sales agents order only for accounts they own; fulfilment steps need the order:fulfil permission (admins, managers).
  • Customers see confirmed orders of their own accounts with a progress tracker (received → being prepared → on its way → delivered), never drafts or internal notes.
  • Migration 0005. Documentation: docs/orders.md.

Checked backend 427 tests; frontend 108 component and 32 end-to-end tests. Security "mutation checks": rules were broken on purpose to prove the tests catch it.

Step 12 — Invoices, credit notes and payments (Phase 13)

  • An invoice is created from an order as a draft (no number). Issuing gives it the next number (INV-0001…) — numbers have no gaps because a discarded draft never had one.
  • Issued invoices are frozen by the database itself (a trigger): only the running balance can change. Corrections are made with credit notes (CN-0001…), whose reason the customer sees.
  • Payments are entered by hand; they cannot be edited or deleted. A mistake or bounced transfer is undone with a reversal entry. Customers only see payments that count.
  • Amount due = total − credit notes − payments; never negative (no overpayments). Payment state (Open, Partially paid, Overdue, Paid, Credited) is calculated on every read.
  • Admins and managers bill and record payments; support and sales agents can only read; customers see issued invoices of their own accounts.
  • Shared money maths moved to backend/app/core/money.py. Migration 0006. Documentation: docs/invoices.md.

Checked backend 490 tests (8 security mutations caught); frontend 119 component and 35 end-to-end tests; production build OK.

Step 13 — Follow-up: invoiced orders can no longer be cancelled

The invoices module tells the orders module through a small public function (no direct writes into another module's tables). Migration 0007.

Step 16 — "I cannot log in; users should be creatable": user onboarding (ADR 0004)

You asked to be able to create users, and chose both ways: administrators create users, and people can sign up on the login page but get access only after approval. Because this changes how people enter the system, it was written down first as ADR 0004 and built only after your approval.

  • Keycloak now stores its data in PostgreSQL (its own keycloak database). Before, it kept users inside its container, so created users would have been lost on every restart.
  • Mailpit was added: a local e-mail inbox at http://localhost:8025. Every e-mail the login system sends (verification, invitation, password reset) lands there and never reaches the real internet.
  • A login on its own grants nothing. A person needs a CRM user in exactly one organisation, and only an administrator can create that link.
  • Three ways in: (1) a Tenant Admin adds a staff member on the Users page; (2) staff invite a customer contact from an account page ("Portal access"); (3) someone signs up, enters the organisation's sign-up code, and waits until an admin approves (choosing a role, or "customer" plus accounts).
  • Safety rules: Super Admin can never be given out; admins can't change or deactivate themselves; the last Tenant Admin can't be removed; 5 wrong codes per hour at most; the e-mail must be verified; deactivating signs the person out everywhere at once.
  • Passwords are never seen by the CRM: people set them on Keycloak's own page from the e-mail link.
  • Migration 0008; documentation in docs/onboarding.md.

Bugs found and fixed along the way:

  • The "Last sign-in" column always said "Never". Sign-ins are now recorded, at most every 15 minutes.
  • A dangerous one: after a failed first try, the approval form could jump back to "Sales Agent" while still looking like "Customer". It was fixed so what you see is always what is sent, and a test guards it.
  • Several dialogs on one page reused the same field IDs, so labels pointed at the wrong fields (bad for screen readers). Each dialog now has unique IDs.

Checked backend 547 tests (including the real Keycloak and Mailpit); frontend 124 component tests; 38 end-to-end tests, including a real invitation e-mail opened from Mailpit.

Step 17 — The AI assistant, text chat (Phase 20a)

You asked to start the AI assistant. It was split into small steps: 20a text chat (done), 20b knowledge base with pgvector (later; needs a different PostgreSQL image), 20c voice (later).

  • Customers ask in the portal: "Where is my order?", "Which invoices are still open?".
  • The assistant (Claude) can only use tools. Each tool calls the same functions as the portal pages, as the signed-in customer, so it can never see more than the customer could open themselves.
  • It has no way to change data. Its only "action" prepares a support ticket; the customer must click Create ticket.
  • Protection against manipulation (prompt injection): even if someone hides instructions in data (e.g. an order reference saying "ignore your rules") and the model obeys, the server refuses anything outside the customer's own data. Tests prove this with a deliberately misbehaving stand-in model.
  • Limits: 30 messages per hour, 2,000 characters per message, 6 tool steps per answer. Every tool call is written to an audit table that can't be changed.
  • The Claude API key stays in backend\.env; the browser never sees it. Without a working key the portal honestly says "not available" and offers a ticket.
  • Migration 0009; documentation in docs/assistant.md.

Checked backend 569 tests passing (+4 live evaluations that run only on request); 127 component tests; 40 end-to-end tests.

Step 18 — Connecting Claude: lessons about API keys

Connecting the real Claude API took several attempts. The lessons are worth keeping:

  1. Never paste a key into a chat, ticket or screenshot. A key that was shown anywhere must be revoked and replaced. Keys pasted in this chat were treated as exposed and never used.
  2. Store keys with the helper. It reads the key without showing it and writes it to backend\.env: 
    cd /d E:\crm-lead\backend
.venv\Scripts\activate
python -m scripts.set_anthropic_key
  3. Check the connection yourself (it shows only the key type and Anthropic's answer, never the key): 
    python -m scripts.check_anthropic
  4. Key types: sk-ant-api… = workspace key (simplest). sk-ant-usr… = user-level key: it needs a workspace ID (setting CRM_ANTHROPIC_WORKSPACE_ID), and must belong to the organisation that has the credit.
  5. "Credit balance is too low" means the key isn't billed to an organisation with credit. The console's Workbench can still work (it uses your browser login), so test with check_anthropic.
StatusThe live check against real Claude is still open: the last test still answered "credit balance is too low". Once check_anthropic says WORKS, the live check takes a few minutes.

5. Your own account: sign-up, the e-mail inbox, joining an organisation

1. Verify your e-mail in Mailpit (not Gmail)

  1. Open http://localhost:8025.
  2. Click the newest "Verify email" message to your address.
  3. Click the link inside. You are taken back to the CRM.

2. Request access with your organisation's sign-up code

Enter the organisation's sign-up code (a Tenant Admin sees it on the Users page) and click Request access. The page then shows "Waiting for approval".

3. Approve (as the organisation's admin)

  1. Open a private/incognito browser window and go to http://localhost:3000.
  2. Sign in as alpha.admin (password: E2E_USER_PASSWORD in frontend\.env.local).

4. Continue

Back in your own window, click Check again, then Continue to crm-lead. You're inside with the role chosen.

6. Security: how data is protected

ProtectionWhat it means
Tenant isolationEvery business table has tenant_id. It comes only from the verified user record, never from the browser. Composite foreign keys make the database itself refuse links between tenants.
Role permissions (RBAC)Every endpoint requires a permission such as invoice:manage.
Record-level rulesEven with the permission, you only see rows you may see (e.g. an agent's own accounts). Lists are filtered inside the database, so counts never leak.
404 instead of 403A record you may not see answers "not found", so nobody can probe which IDs exist.
Never trust browser IDsEvery ID is loaded through the policy; tampering gives 404 (tested).
Server-controlled fieldsTotals, numbers, statuses, creators are never accepted from the browser (unknown fields are rejected with 422).
No tokens in the browserOnly an encrypted httpOnly cookie; tokens stay on the server.
Append-only recordsAudit log, ticket comments, order history, invoice lines, payments, credit notes cannot be changed by the API's database role.
Database guardsCheck constraints (totals add up, balance never negative), a trigger freezing issued invoices, unique indexes (one live invoice per order).
No secrets in codeAll secrets come from git-ignored .env files; examples use placeholders.
Joining needs an administratorA login alone grants nothing; only an admin links a person to an organisation and role. Sign-up codes are random and attempts are limited.
AI assistant boundariesThe model only gets tools that run as the customer; it can't write data; hand-overs need the customer's click; every tool call is audited; nothing of other customers is ever sent to the model (tested).
Still plannedPostgreSQL Row-Level Security (RLS) as an extra safety net is scheduled for Phase 5 (tenancy); today isolation is enforced by the policies, foreign keys and tests.

7. How we test, and the results

  • Backend (pytest): runs against a real PostgreSQL test database crm_test; each test runs inside a transaction that is rolled back, so tests never leave data behind. Every module tests: happy path, validation, tenant isolation, role denial, record-level denial, ID tampering.
  • Mutation checks: a security rule is broken on purpose; at least one test must fail; then the code is restored.
  • Frontend component tests (Vitest): forms, buttons, dialogs, display rules.
  • End-to-end tests (Playwright): a real browser logs in through Keycloak and clicks through complete journeys as different users (agent, manager, support, customers of two tenants).
  • Code quality: ruff (lint/format) and mypy (types) for Python; ESLint, Prettier and TypeScript strict mode for the frontend.

8. How to run everything yourself (Windows CMD)

All commands start from the project folder E:\crm-lead. Use a normal Command Prompt.

1. Start the services (database and login server)

cd infrastructure
docker compose up -d
docker compose ps

Wait until both show healthy. To stop them without losing data: docker compose down (never add -v, which deletes the data).

2. Start the API (new CMD window)

cd backend
.venv\Scripts\activate
alembic upgrade head
uvicorn app.main:create_app --factory --reload

activate switches to the project's own Python; alembic upgrade head applies any new table changes; uvicorn starts the API on http://127.0.0.1:8000.

3. Start the website (another CMD window)

cd frontend
npm run dev

Open http://localhost:3000 and sign in.

13. Glossary

TermMeaning
APIThe backend's "doors" that the website (or the future assistant) calls to read or change data.
TenantOne organisation using the CRM. Tenants never see each other's data.
AccountA customer company in the CRM.
LeadA possible customer that has not bought yet.
RBACRole-Based Access Control: what you may do depends on your role's permissions.
OIDC / PKCEStandard, secure ways to sign in through a login server (Keycloak).
TokenA signed, short-lived proof of who you are, checked on every API call.
MigrationA numbered script that changes the database structure in a repeatable way.
TransactionA group of database changes that happen all together or not at all.
Optimistic lockingDetecting that someone else changed a record since you loaded it (version number).
Audit logA permanent record of who changed what and when.
SnapshotA copy of values at one moment (order/invoice lines keep their prices forever).
Credit noteA document that reduces what a customer owes on an issued invoice.
ReversalAn entry that cancels a mistaken payment without deleting it.
SLAService-level agreement: the promised response and resolution times for tickets.
ADRArchitecture Decision Record: a short note explaining one important decision.
Mutation checkDeliberately breaking a rule to prove the tests notice.
End-to-end testA test that uses the real website in a real browser, like a person.
